# 行程保存性能优化

日期：2026-10-10。

本轮针对实际会话中“完整行程生成 → 保存失败 → 整份重写”的耗时，独立于供应商并发、
限流和前端进度开发。保留 DeepSeek Flash/high、完整原始模型消息和工具历史；不新增
上下文、输出或工具次数上限，不固定查询、提问或交付步骤。

## 保存失败后局部修正

`save_itinerary` 新增可选 `retry_from_call_id`。模型可以引用**本轮最近一次失败保存**
工具结果中的 `call_id`，配合 `patch` 和 `change_reason` 修正错误，首份方案尚未成功
保存时也适用。例如：

```json
{
  "retry_from_call_id": "call_failed_save",
  "patch": {
    "costs": [{"id": "disney", "kind": "unknown", "total": null}],
    "items": [{"id": "hotel_checkin", "start": "2026-10-11T13:15:00+08:00"}]
  },
  "change_reason": "修正未知费用口径和转场时间"
}
```

已有已发布版本时仍须提供当前 `base_version_id`，首份为 null。未指定的原有来源导入
和解除保护依据继承；显式提供 `available_source_ids` 或 `release_protections` 时替换
对应列表。条目仍按稳定 ID 递归合并，数组仍替换，字典的未指定字段仍保留。

服务从同一 run 的已提交 journal 重建失败候选，支持连续失败修正链；不依赖进程内
候选缓存、不接受其他 run、成功保存或更早的失败调用。重建后依旧导入真实来源、校验
全部 Pydantic 字段、用户原话、当前版本、锁定、报价与时间安排。修正未成功时仍撤销
本轮已有草案，不发布有冲突的候选。程序不自动改时间或补费用；修改由模型决定。

原始失败参数、错误反馈和每次修正参数均保持原样持久化并回传模型。重启后可从 journal
恢复修正链，无新表或迁移。

## 将关联规则暴露给模型

费用字段直接解释 `unknown + null` 与 `reference/query_quote + 数值 + 来源` 的要求。
未核实的自主估算可说明在 `basis.calculation`，不能伪造供应商来源。转场字段直接说明
间隙为“前项结束至后项开始”，须容纳行驶加缓冲；交通块已有行驶时长不得在相邻间隙
重复计算。景点开放区间属于 `opening_hours`，不等同于必须完整预留的固定安排。

这些说明不降低已有校验标准，也不增加固定业务步骤。

## 减少附加索引重复

内部行程索引保留完整 canonical document、review、版本身份及费用差值；diff 的每条
变化只重复提供 section/id/operation/fields，省去与完整 document 重复的 before/after。
完整 diff 仍保存在数据库、公共版本 API 和原始工具历史中。没有摘要、裁剪或替换原始
会话历史，不改变 UI 旧版查看和差异展示。

## 验证与测量范围

`tests/test_itinerary_save_optimization.py` 覆盖首次 schema 失败 → 局部修正 → 时间冲突
→ 再次局部修正 → 成功发布；同时验证完整历史、锁定保护、来源继承、引用边界和运行时
重启后恢复。原有行程版本、行程校验和图运行回归仍须通过。

以本次真实上海四天会话的已持久化数据只读计算：两次完整重试参数分别为 16,629 和
16,713 字符，等价局部 patch 为 1,505 和 2,400 字符，减少约 90.9% 和 85.6%。
第二次比较重建后字段一致；第一次重建后完整 Pydantic 模型一致，仅保留了原有默认
null 字段。模型附加行程索引由 56,596 降至 42,802 字符，减少约 24.4%。

以上是参数与附加上下文大小的测量，不是新一轮真实模型耗时对照。模型仍自主决定是否
使用 patch，实际提速取决于模型输出、返工次数和供应商响应；不承诺固定秒数。

为避免与并行开发争抢部署，不在本轮重启本地服务或改 `.env`。加载新工具定义需要
服务后续正常重启；已执行中的旧运行继续遵守其版本围栏。
